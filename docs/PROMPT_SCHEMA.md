# Схема генерации тестов через LLM

## Обзор

Система генерации тестов использует LLM (Large Language Model) для создания тест-кейсов на основе описания требований. Система поддерживает три типа тестов: `manual`, `api`, `ui`.

## Архитектура

### Основные компоненты

1. **PromptEngineer** (`backend/core_agent_service/app/services/prompt_engineer.py`)
   - Формирует system и user промпты для LLM
   - Валидирует входные данные
   - Адаптирует промпты под тип теста

2. **test_generation.py** (`backend/core_agent_service/app/tasks/test_generation.py`)
   - Celery задача для асинхронной генерации
   - Вызывает LLM через LLMClient
   - Парсит ответ LLM и извлекает код/текст
   - Обрабатывает несколько файлов и описания

3. **LLMClient** (`backend/core_agent_service/app/services/llm_client.py`)
   - Отправляет запросы к LLM API
   - Обрабатывает ответы разных форматов
   - Ретраи при ошибках

## Схема промпта

### Структура промпта

Промпт состоит из двух частей:
- **System Prompt** — определяет роль и требования к ответу
- **User Prompt** — содержит конкретное задание и требования

### Типы тестов и их промпты

#### 1. Manual тесты (`test_type="manual"`)

**System Prompt:**
- Роль: QA-инженер по ручному тестированию
- Формат: Только текст, без кода и Markdown
- Структура: Заголовки, предусловия, нумерованные шаги, тестовые данные, ожидаемые результаты

**User Prompt:**
- Описание требований
- Feature/Story (опционально)
- Требования к структуре: шаги, данные, результаты, негативные сценарии

**Ожидаемый ответ:**
- Структурированный текст с тест-кейсами
- Сохраняется как один файл `test_case.txt`

#### 2. API тесты (`test_type="api"`)

**System Prompt:**
- Роль: Генератор Python-кода тестов
- **КРИТИЧЕСКИ ВАЖНО:** Ответ должен начинаться СРАЗУ с ```python
- Запрещено: текстовые пояснения типа "We need to...", планы действий
- Обязательно: готовый код в markdown блоке

**User Prompt:**
- Описание API эндпоинтов
- Feature/Story (опционально)
- Строгое требование: начать с ```python без текста перед ним
- Требования к коду: pytest, httpx, Allure, AAA, позитивные/негативные сценарии

**Ожидаемый ответ:**
- Код в markdown блоке ```python ... ```
- Может быть несколько блоков (несколько файлов)
- Описания могут быть между блоками

**Парсинг:**
- Извлекаются все блоки ```python ... ```
- Текст перед блоком → описание файла
- Каждый блок → отдельный файл
- Если блоков нет, ищется код, начинающийся с `import/from`

**Структура результата:**
```json
{
  "test_case": {
    "files": [
      {
        "description": "Описание файла (может быть null)",
        "code": "import pytest\n...",
        "filename": "test_1.py"
      },
      {
        "description": "Описание второго файла",
        "code": "import pytest\n...",
        "filename": "test_2.py"
      }
    ],
    "raw_response": "Полный ответ LLM"
  }
}
```

#### 3. UI тесты (`test_type="ui"`)

**System Prompt:**
- Роль: QA-инженер по UI/E2E
- Формат: Код в markdown блоках с пояснениями
- Требования: pytest + Playwright, Allure, AAA, селекторы, скриншоты

**User Prompt:**
- Аналогично API тестам
- Требования к UI-специфичным элементам

**Ожидаемый ответ:**
- Аналогично API тестам
- Код в markdown блоках

## Процесс генерации

### Шаги выполнения

1. **Валидация входных данных** (0-20%)
   - Проверка description (10-10000 символов)
   - Проверка test_type (manual/api/ui)
   - Проверка feature/story (макс 200 символов)

2. **Формирование промптов** (20-40%)
   - PromptEngineer создаёт system и user промпты
   - Промпты адаптируются под тип теста

3. **Вызов LLM** (40-80%)
   - Отправка запроса к LLM API
   - Получение ответа
   - Если ответ не содержит код (для api/ui) → повторный запрос с усиленным промптом

4. **Парсинг ответа** (80-100%)
   - Для api/ui: извлечение блоков кода из markdown
   - Для manual: сохранение текста как есть
   - Формирование структуры с файлами и описаниями

### Обработка ошибок

**Если LLM не вернул код:**
1. Логируется предупреждение с preview ответа
2. Отправляется повторный запрос с усиленным промптом
3. Если и второй раз нет кода → LLMError

**Ретраи:**
- Максимум 3 попытки
- Задержка между попытками: 60 секунд
- После всех попыток → TaskError

## Парсинг ответа LLM

### Функции парсинга

#### `extract_code_blocks_from_markdown(txt: str) -> list[dict]`

Извлекает все блоки кода из markdown с описаниями.

**Алгоритм:**
1. Ищет все паттерны ```python ... ``` или ``` ... ```
2. Для каждого блока:
   - Текст перед блоком → `description`
   - Содержимое блока → `code`
   - Генерируется `filename` (test_1.py, test_2.py, ...)
3. Текст после последнего блока → добавляется к описанию последнего файла

**Возвращает:**
```python
[
  {
    "description": "Описание или None",
    "code": "import pytest\n...",
    "filename": "test_1.py"
  },
  ...
]
```

#### `extract_code_from_text(txt: str) -> dict`

Универсальная функция извлечения кода.

**Алгоритм:**
1. Пробует извлечь из markdown блоков
2. Если нет блоков → ищет код, начинающийся с `import/from`
3. Если код найден → создаёт один файл с описанием (если есть текст перед кодом)
4. Если код не найден → возвращает весь текст как один файл

**Возвращает:**
```python
{
  "files": [...],
  "raw_response": "Оригинальный ответ LLM"
}
```

#### `has_code(txt: str) -> bool`

Проверяет наличие кода в ответе.

**Проверяет:**
- Наличие markdown блоков ```python
- Наличие строк, начинающихся с `import ` или `from `

## Примеры

### Пример 1: Один файл API тестов

**Ответ LLM:**
```
```python
import pytest
import httpx
import allure

@pytest.fixture
async def client():
    async with httpx.AsyncClient() as ac:
        yield ac

@allure.feature("ВМ")
async def test_get_vms(client):
    response = await client.get("/vms")
    assert response.status_code == 200
```
```

**Результат:**
```json
{
  "files": [{
    "description": null,
    "code": "import pytest\n...",
    "filename": "test.py"
  }]
}
```

### Пример 2: Несколько файлов с описаниями

**Ответ LLM:**
```
Первый файл содержит базовые тесты для GET эндпоинтов.

```python
import pytest
# ... код для GET тестов ...
```

Второй файл содержит тесты для POST эндпоинтов.

```python
import pytest
# ... код для POST тестов ...
```

Дополнительные тесты для edge cases.
```

**Результат:**
```json
{
  "files": [
    {
      "description": "Первый файл содержит базовые тесты для GET эндпоинтов.",
      "code": "import pytest\n...",
      "filename": "test_1.py"
    },
    {
      "description": "Второй файл содержит тесты для POST эндпоинтов.\n\nДополнительные тесты для edge cases.",
      "code": "import pytest\n...",
      "filename": "test_2.py"
    }
  ]
}
```

## Сохранение промпта

Промпт сохраняется в результате для отладки:

```json
{
  "prompt": "System Prompt:\n...\n\nUser Prompt:\n..."
}
```

Это позволяет:
- Понять, что именно отправлялось в LLM
- Отладить проблемы с генерацией
- Улучшить промпты на основе реальных ответов

## UI отображение

### TaskDetailsPage / TasksPage

- Отображает каждый файл отдельно
- Показывает описание файла (если есть)
- Кнопка "Скачать файл" для каждого файла
- Кнопка "Скачать архив (ZIP)" для всех файлов
- В архиве создаётся README.md с описаниями всех файлов

## Рекомендации по улучшению

1. **Если LLM не возвращает код:**
   - Усилить system prompt с примерами
   - Добавить few-shot примеры в user prompt
   - Использовать более строгие инструкции

2. **Если код неполный:**
   - Увеличить `max_tokens` в запросе к LLM
   - Разбить генерацию на несколько запросов

3. **Если несколько файлов:**
   - Явно просить LLM разделять файлы
   - Использовать шаблоны имен файлов в промпте
